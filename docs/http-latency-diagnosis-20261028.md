# HTTP 54–56 ms 延迟定位

> 本文保留修复前的诊断数据。后续已修复 HTTP 服务端并通过原 20 ms 时延项验收，当前结果见 [修复与验收](http-latency-validation-20261028.md)。

**主因在测试床 HTTP 应用与 TCP 发送方式的配合。** 对照实验支持“响应头/正文分两次发送，Nagle 小包合并与延迟 ACK 叠加”的解释；硬件算力不足、5G 控制面交互失败均不符合本次主导延迟的表现。结果见 [结构化证据](http-latency-diagnosis-20261028.json)。

HTTP 指标从 `connection.request()` 前开始，到 `response.read()` 读完整个正文结束，包含完整应用事务，并非空口单向时延。当前服务用 Python `BaseHTTPRequestHandler`，`end_headers()` 与 `wfile.write(body)` 分开发送；连接未显式禁用 Nagle。

诊断复用 `oai-acceptance-20261028-4`，每次读取 1200 字节。原运行镜像、业务进程、生产监听、原有连接选项及系统 TCP 配置均未修改。隔离回环服务仅监听容器内随机回环端口，测完关闭；真实路径探针仅发有限次 GET。

| 对照 | 响应头耗时中位数 | 等正文中位数 | 完整事务中位数 |
|---|---:|---:|---:|
| 原应用实现，容器内回环，32 次 | 0.31 ms | 43.77 ms | 44.06 ms |
| 回环，仅服务端 TCP_NODELAY，32 次 | 0.15 ms | 0.02 ms | 0.17 ms |
| 回环，仅客户端 TCP_NODELAY，32 次 | 0.32 ms | 43.70 ms | 44.00 ms |
| 原 UE→RAN→free5GC→应用路径，24 次 | 6.52 ms | 48.07 ms | 54.86 ms |
| 同路径，探针收到响应头后 TCP_QUICKACK，24 次 | 5.86 ms | 5.97 ms | 11.74 ms |
| 同路径，恢复原探针方式，24 次 | 5.84 ms | 47.02 ms | 52.91 ms |

回环对照不经过 OAI、free5GC 或 RFsim，仍重现约 44 ms；真实路径只改变探针 ACK 行为，就减少约 43 ms，恢复原方式后延迟重现。因此原来的 54–56 ms 主要不是无线仿真算不动，也不能归咎为 HTTP 协议必然如此或 OAI/free5GC 的协议缺陷。应用实测约占 0.027 个 CPU 核，配额为 1；UDP/ICMP 同期约 5–7 ms。剩余真实路径开销包含 RAN、TCP 往返与调度，本次未逐段拆分。

修复应优先在 HTTP **服务端**对新连接启用 `TCP_NODELAY`，或把响应头和小正文合并写出；仅设置客户端 `TCP_NODELAY` 的回环对照没有改善。随后以相同负载和原 20 ms 条件重新验收，区分响应头、正文等待与完整事务指标。

**11.74 ms 是诊断探针结果，不能替换原业务流的 SLA 验收。** 原业务实现尚未修改，诊断后两条原 HTTP 流仍约 54.6/57.1 ms，六条业务均健康、原容器未替换或重启。原始样本和哈希保存于本机及服务器 `experiments/oai-acceptance-20261028/http-diagnosis/`。
